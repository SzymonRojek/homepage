How I test at work

At Equiniti I test financial and shareholder data as it moves between systems. I try to look at a migration from above, so I see the same record as data, as business logic and as code. Clients and figures are confidential, so this is my approach, not a project report.

Beyond the obvious bugs

Sometimes I was right. That gave me far more satisfaction than finding the obvious bugs.

More than once I found bugs not only in the data that came with a code drop after a deployment, but in the stored procedures themselves.

Sometimes there was no data to test yet. I like to analyse and dig, so I read the stored procedures and checked them against the business requirements and the mapping documents, and asked the solution designers more questions. Several times I set up a call with the developer who wrote the code, to go through an interesting case together.

  1. 01

    Understand the rules, then design the tests

    I turn requirements, mapping documents and transformation rules into positive and negative test cases, each traceable back to the rule it checks and peer-reviewed before anything is run.

  2. 02

    Reconcile with SQL and check the logic

    Record counts, totals, field-by-field values, empty values, duplicates and relationships between tables. A number can match and still be wrong, so I also check results against the business rules and read the stored procedures that transform the data.

  3. 03

    Trace each defect to its root cause

    Is it the data, the transformation logic, a stored procedure or the requirement itself? I log it in Azure DevOps with reproduction steps and evidence, and retest the fix with the developers.

Why it matters: In financial data, one wrong field can mean a wrong holding or a wrong payment. Reconciliation proves that nothing was lost or changed on the way.

Case study

Talent Outreach: job offers to the right candidates

  1. 1

    Brief

    A small recruitment agency keeps its candidates in a spreadsheet. Every new job offer means filtering by hand, pasting addresses into Gmail and writing “Dear candidate”, with the risk of leaking addresses or contacting the same people too often.

  2. 2

    Research

    Spreadsheet and GmailMy design
    Filter the sheet by hand and copy the addresses.Pick a role and a budget, and the matching candidates are found.
    “Dear candidate” for everyone.Every email uses the candidate's name and the role, and a mistyped placeholder is caught before sending.
    Nobody remembers who got which offer.Candidates contacted in the last 14 days are skipped by default, and the list shows when each one was last contacted.
    Consent is a column nobody updates.Only candidates open to offers get emails, and the opt-out link in every email updates the status by itself.
    One address in CC instead of BCC leaks everyone's email.One email per candidate, so nobody sees the others.
    What was sent is buried in the Sent folder.An outbox for each job offer shows who got it and every email exactly as it was sent.
  3. 3

    Solution

    • A server-only path to the data: the Airtable token never reaches the browser.
    • A one-click “Try the demo” login that exists only where the demo is switched on; API clients use a password, with a 15-minute lockout after 5 wrong attempts.
    • The browser suggests the recipients, and the server has the last word: it sends only to candidates open to offers.
    • Every email is built on the server from one template: personalised, escaped and with a signed opt-out link. The preview uses the same template.
    • An outbox instead of real sending, so the public demo can't email anyone.
    • Staging before production, a nightly demo reset followed by a read-only check of the live app, and error monitoring without personal data.
  4. 4

    Value

    • Fewer costly mistakes: no CC leaks, no offer twice within two weeks and no email to anyone without consent.
    • From a role and a budget to personalised offers in one flow, with a preview before every send.
    • Safe to hand over and change: tests at every level, CI on every pull request and staging before production.

    Not built yet: real delivery. Every email is built, checked and saved to the outbox; sending it through an email service is one more transport in one file. Airtable's free plan also caps a base at 1,000 records and 1,000 API calls a month, so a bigger talent pool needs a paid tier.

Problem

The app started in 2021 as an email CRUD client that sent emails through EmailJS straight from the browser. The Airtable key sat behind an Express proxy, but the login ran only in the browser: anyone who called the API directly could read, change or delete every record. My first review found 11 bugs.

In 2026 I rebuilt it to production standard and then narrowed it from a generic newsletter tool to one recruiter's problem: the right job offer to the right candidates, and not to anyone contacted in the last 14 days.

Constraints

  • Airtable is the database: a third-party REST API with rate limits and pages of 100 records.
  • Candidate data is personal data: consent, an opt-out in every email and no personal data in monitoring.
  • A public demo anyone can enter with one click: no real emails, visitors change the data, and only made-up data belongs in it.
  • Free hosting (Render) that sleeps after inactivity and blocks outgoing email (SMTP).
  • One maintainer, so every change has to be checked automatically and on staging before production.

Architecture

Runtime: the browser never talks to Airtable

  1. React app
  2. Express API under /api with a signed login token
  3. Server checks consent, escapes text, signs opt-out links
  4. Airtable: candidates, job offers, outbox, feedback

Delivery: feature branch to production

  1. Feature branch off dev
  2. Pull request: type check, lint, unit tests, build
  3. Playwright e2e, Postman API tests and Lighthouse against a fake Airtable
  4. Merge to dev, auto-deploy to staging
  5. Check staging
  6. Release pull request dev to main, CI again on all changes together
  7. Auto-deploy to production

Testing, performance, accessibility and security

Testing
Server tests with Jest and supertest cover every endpoint, login and limits, sending and templates, opt-out links, the CSV import, feedback, the demo reset and privacy in monitoring, with Airtable mocked. Client tests with Vitest and React Testing Library cover validation, CSV, search, sorting and filtering, the API client and choosing recipients by role, budget and last contact. Playwright runs 63 user flows on the production build, from a job offer draft to the outbox, opting out, unsaved changes, dark mode and phones. A Postman collection of 30 requests, run by Newman in CI, tests every endpoint from the outside, and its read-only smoke folder checks the live app after every nightly reset.
Performance
The server follows Airtable's paging, so lists show every record and not only the first 100. Approved feedback is kept in memory for 30 seconds and the nightly reset is skipped when nothing changed, both to stay within Airtable's API limits. Lighthouse reports performance on 7 screens; its limit only catches a real slowdown, because scores vary on shared CI machines. On the free plan the main cost is a cold start of up to a minute, which the README tells visitors about.
Accessibility
The UI is built on shadcn/ui and Radix primitives, which handle keyboard and screen-reader support for dialogs, menus and side panels. Lighthouse audits 7 screens, logged out and in, on every pull request and fails it below 100 for accessibility; it already caught a low-contrast avatar and a button without a name. End-to-end tests find controls by their role and accessible name, and phone layouts have their own tests.
Security
The Airtable token lives only on the server and error responses no longer leak it. Login tokens are HMAC-signed and expire after 8 hours, with constant-time comparisons and a lockout on the visitor's real address. The demo login exists only where it is switched on. Opt-out links have their own signature, user text is escaped in every email, the server has no CORS, and public feedback has a bot trap, a rate limit and moderation.

Lessons learned

  • A review found the Airtable token leaking in error responses. Anything a server returns on failure needs the same care as a success response.
  • Unchecking every recipient sent the email to all of them: an empty selection was treated as “no filter”. Edge cases like an empty list deserve their own test.
  • Lists silently stopped at 100 records because Airtable pages its results. Testing with more data than one page is cheap and catches this.
  • Monitoring can leak too: opt-out tokens in page addresses had to be removed from error reports before they were sent.
  • Lighthouse in CI caught what the tests missed: a low-contrast avatar and a button without an accessible name.
  • A public demo needs product decisions, not only code: an outbox instead of real email, a nightly reset, a one-click login and a request for made-up data.
  • A fake API makes end-to-end tests fast and safe, but only if it behaves like the real one, including its errors.

Problem

Testing, performance, accessibility and security

Testing
Vitest and Testing Library cover logic and components. Playwright runs against the production build in desktop and mobile Chrome, with tests grouped by page section and named steps. Role-based locators also check that every control has an accessible name.
Performance
Lighthouse runs three times on every push and fails CI if the median performance score drops below 0.85 or layout shift goes above 0.1. Self-hosting the font and resizing the photo raised the mobile score from 0.84 to about 0.9 and brought the first paint forward from 3.0 s to 2.2 s. The build also writes the whole page into the HTML, so it can be read without JavaScript, and in the light theme React takes it over as it is, so the photo isn't drawn twice.
Accessibility
axe scans the page in the light and dark themes with every case study expanded, and any serious or critical violation fails the build. Lighthouse accessibility must stay at 95 or above. The page uses semantic headings, landmarks and labelled lists.
Security
No secrets and no runtime API calls. npm audit fails CI on high-severity advisories in the code shipped to visitors, and Dependabot proposes updates every week. External links use rel=“noreferrer”. Development-only tools still carry some advisories, but they never reach the browser.

Lessons learned

  • A bug I couldn't reproduce, a light flash on reload, became solvable once I wrote a failing test that recorded the background colour on every frame.
  • A fix can look broken because of browser caching. I now check what the server actually serves before changing the code again.
  • When removing well-tested code lowered coverage, I added tests for real branches instead of lowering the threshold.
  • End-to-end tests hard-code the text a visitor sees instead of importing it from the data files, so a content mistake can't pass by testing itself.
  • Lighthouse CI judges the best of three runs by default. I switched to the median so the budget can't pass by luck.
  • Mutation testing with Stryker showed that 80%+ coverage hid real gaps: a saved dark theme, the state on page load, the commas between interests and the content of each case-study section were never checked. After targeted tests, every mutant in those files was caught. The tool needed checking too: a runner bug first reported 13.6% because no tests ran for most mutants.
  • A flaky end-to-end test pointed to a real race: a case-study link that changed the address just after the page loaded was ignored, because React had not attached its listener yet. A unit test now reproduces it, and the page reads the address again once the listener is ready.
  • After the redesign, Lighthouse performance dropped below the budget. The cause was a small pulsing dot: its animated shadow made the browser repaint on every frame. Animating only its size and opacity moved the work off the main thread, and the score went back above the budget.
  • A photo that seemed to flicker on every reload was the text reflowing: the page first appeared in a fallback font, and the photo moved when the web fonts arrived. Preloading the fonts in the HTML fixed it and brought the first paint forward from about 2.2 s to 1.6 s.
