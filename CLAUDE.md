## Project overview

Personal portfolio homepage of **Szymon Rojek**, Test Engineer (data migration, SQL and API testing) who also builds front-end.
Live: https://szymonrojek.com/ (GitHub Pages with a custom domain bought at Cloudflare; `public/CNAME`, `homepage` field in `package.json`). The old https://szymonrojek.github.io/homepage/ redirects there.

A single page aimed at recruiters for test automation and QA roles (developer roles possibly too, through the `#case-study-talent-outreach-developer` link). The theme of the page is a tester who also builds software (the duotone portrait, the projects' code and test colours, and the footer's question), told with as little repetition as possible: each fact lives in one place. The design is a "colour block": the page opens and closes on near-black with a green undertone (`brand.dark`, `#0B1513`: the hero and the footer), the deep brand green (`brand.background`) is the one strong colour inside it (the raised top bar, the featured project card, and the How I test band in the dark theme), with cream text and a sunny yellow accent, around a warm sand page (`#F4EAD6`) with white bands and cards that alternate down the page (redesigned on 2026-10-16 after a reference page the user picked). Testing is green (`theme.colors.qa`), code is terracotta (`theme.colors.dev`). Headings use Bricolage Grotesque, body text Geist, tiny labels and the section numbers Geist Mono (the reference page's fonts; Plus Jakarta Sans and Inter before 2026-10-16). Parts in order (sections: How I use AI, How I test, Projects, Experience, Skills, References, each with a small numbered heading, "01 / How I use AI" and so on):

## Git workflow (mandatory)

`main` is production: every push to it deploys the live site. These rules are fixed; do not change or skip them, and do not treat an earlier approval as permission for a later step.

1. Work and commit on the **`dev`** branch only. Never commit on `main`.
2. **Always ask the user before any `git push`**, including to `dev`. Wait for an explicit yes.
3. Changes reach `main` only through a **Pull Request `dev → main`** that **the user merges** on GitHub. Open the PR only when the user asks; never merge it yourself.
4. `main` always comes last: local checks → push to `dev` (CI runs lint, typecheck and tests, no deploy) → user reviews → PR → user merges → deploy.

This is enforced in four places:

- **GitHub ruleset on `main`:** no direct pushes, PR required, CI must pass, no bypass (not even for the admin account the agent uses).
- **`.claude/settings.json`:** `deny` blocks `git push` to `main` and `gh pr merge`; `ask` requires approval for every other `git push`.
- **CI:** `.github/workflows/ci.yml` deploys only from `main`.
- **GitHub Pages:** the site is published only by that deploy job (Pages' source is GitHub Actions, and the `github-pages` environment is limited to `main`), so there is no branch to push to and no manual deploy.

## Conventions (follow these)

- **Component layout:** `ComponentName/index.tsx` holds the JSX and `ComponentName/styled.ts` holds the styled-components. Small style-only primitives can live in `index.ts` alone (`ButtonLink`, `Section`).
- **Named exports** for components (`export const Footer = () => ...`). Slices default-export their reducer and name-export actions and selectors.
- **Selectors:** each slice defines a private `selectXState` and exports `selectX` helpers built on it.
- **Types:** strict TypeScript, no `any`. Type props with an interface next to the component. Unused function arguments are prefixed with `_`.
- **Theme tokens only:** never hard-code colours or breakpoints.
  - Use `theme.colors.*` (including `brand`, `dev`, `qa`, `primary` / `primaryHover` / `onPrimary`, `terminal`), `theme.breakpoints.mobileMax | tabletVerticalMax | tabletHorizontalMax`, `theme.boxShadow`, `theme.borderRadius` (cards, 8px), `theme.borderRadiusSmall` (4px: buttons, tags, badges, links), `theme.fontDisplay` (Bricolage Grotesque, applied to h1–h4 globally) and `theme.fontMono`.
  - Colour roles: the brand band (`theme.colors.brand`: deep green, cream text, yellow accent) is used for the top bar, the hero and the contact card only. On the cream page, `primary` (deep green in light, yellow in dark) is for buttons and links; green (`qa`) is testing, terracotta (`dev`) is code; the Automation card edge is half and half because it is both. No glows or gradient text.
  - Section backgrounds alternate so each section reads as a block, and the page opens and closes on the same near-black (`brand.dark`: the hero and the footer): How I test sits right under the hero (`storyBand`: white in the light theme, the deep brand green in the dark one), then the page colour (Projects) and bands one step up (`BandSection`, `$band`: `card` for Experience, `quote` for References) take turns with sections on the page colour (Skills), down to the footer: light: dark, sand (How I use AI), white, sand, white, sand, white, dark; dark theme: dark, `#0E2A26` (How I use AI), green, page `#0B1513`, band `#1F302B`, page, band, dark. With six sections, strict alternation inside the light half is impossible if How I test and References both stay white, so How I use AI leads the page on a strong colour instead: both themes then lighten away from the hero and settle into the gentle alternation (light 1.94, 9.55, then 1.19 four times; dark 1.22, 1.25, 1.53, then 1.34). A band under the sticky top bar must never take the theme's `topBar` colour. Bands that follow one another meet edge to edge (`.section-band + &` drops the margin). Neighbouring backgrounds differ by about 1.15:1 or more, enough to see each section as a block without stripes (white next to the old cream was 1.09:1 and ran together). Keep the alternation when a section moves: a white card on a white band needs its border, and a card of the page's tone vanishes on the page (the Skills Learning card became white with a border). Pastel bands per section were tried and dropped (they read as a template and blur what green and terracotta mean), and so was a soft test-green band for How I test.
  - Section headings (`SectionLabel`) are small monospace labels with the section's number in front ("01 / How I test"), as on the reference page, and have no decorative bar above them (a short yellow bar was removed because it read as AI-made). The number comes from `sectionNumber` (`sections.ts`, the page's order) through `data-number` and CSS, so screen readers and the page's text get the name alone; keep `sectionOrder` in step with the page.
  - To add a colour, put it in `colorNames` in `theme.ts` and add the key to **both** themes. `themeDark` is typed as `typeof themeLight`, so a missing key is a type error.
  - Text colours must pass WCAG AA (4.5:1). The axe e2e test enforces this.
- **Buttons:** main actions fill with `primary` and darken on hover (`primaryHover`, about 1.3:1, text still AA); the yellow ones on the green band darken to amber (`brand.accentHover`). Secondary actions (Demo, Code, the × that closes the technical details) share `secondaryButton` from `ButtonLink`: the card colour with a thin border, and on hover the page's tone fills them (`secondaryHover`) and the border darkens. A new button reuses one of these.
- Media queries follow this pattern: `@media (max-width: ${({ theme }) => theme.breakpoints.mobileMax}px) { ... }`. The site is desktop-first.
- **Decorations stay inside the page's width:** the yellow rings (hero top-right, footer bottom-left) and the bug in How I test (top-right) hang off a corner of the content column, not of the window: their side offset adds `columnInset` (`core/App/contentColumn.ts`), so from 1256px up they stop moving with the window and keep the same place next to the content (asked by the user on 2026-10-17; their sides show in full on wide screens). Up to 1256px nothing changes. A new decoration on a full-width band does the same. The e2e `layout` spec measures all three at 1280, 1600, 1920 and 2560px.
- **Vertical rhythm:** one value for the space above and below a section's content, `theme.layout.section` (40px, 24px on phones): a band's padding, the gap before a section on the page colour, and the footer's top. Use it for any new section instead of a number of its own. A section's heading (`SectionLabel`, its first line) adds `sectionOpening` above itself on top of it (32px padding, 24px up to `tabletVerticalMax`, 16px on phones; padding, since a margin would collapse into a page-colour section's margin), so every section opens the same distance down (72 / 64 / 40px), with 16px below the label to the section's big line or content.
- **Page width and gutters:** one content column for everything, from `theme.layout`: at most 1160px of content, centred, with side gutters of 48px on desktop, 32px up to `tabletHorizontalMax` and 16px on phones. Use the `contentColumn` css helper (`core/App/contentColumn.ts`) for anything that must line up with the page edge (the page `Container`, the top bar row and its menu panel, the hero content). Full-width bands (top bar, hero) keep their background edge to edge and put `contentColumn` on an inner element; never add their own side padding. The hero photo ends on the right edge of the column, on phones too, under left-aligned text.
- **SVGs** that need colouring are imported as components with `import XIcon from "./x.svg?react"` and styled through `currentColor`. Decorative images use a plain URL import with `<img src>`.
- **styled-components props** that only drive styling must be transient (`$moveToRight`).
- **Content changes** (profile, skills, experience, projects, quality, email, socials) go into the data files marked CONTENT above, not into JSX.
- **British English** for every word a visitor or README reader sees: "personalised", "colour", "behaviour", "practise" (verb) / "practice" (noun), "organisation". Code identifiers and CSS stay as they are (`color`, `behavior: "instant"`).
- **Fonts:** self-hosted variable woff2 files in `public/fonts/` (Bricolage Grotesque 200–800, Geist 100–900 and Geist Mono 100–900, one file per alphabet for every weight, latin and latin-ext, from @fontsource-variable 5.3.0, OFL; the reference page's fonts since 2026-10-16). The `@font-face` rules live in `index.html` and the two first-screen files (Bricolage Grotesque and Geist, latin) are preloaded there, so the page paints once in its real fonts: no text reflow and no jumping photo on load. Preload `href`s start with `/fonts/` (Vite adds the base); `url()`s in the inline style use `%BASE_URL%`. Don't import fonts from JavaScript again. On a slow connection the page is drawn before the fonts arrive, so each has a fallback face there (`Geist Fallback`, `Bricolage Fallback`, after the real font in the stacks: Arial, Liberation Sans or Roboto, scaled with `size-adjust` and ascent/descent overrides, only for the letters the real fonts have) that breaks lines in the same places, so the swap moves nothing (layout shift 0.056 in PageSpeed before, 2026-10-17; `e2e/fonts.spec.ts` delays the files and checks it). Measure the values again if a font or much of the text changes.
- **Icons** in `public/`: `favicon.svg` (the green "SR" initials in a yellow circle, as in the top bar), `favicon.png` (32px fallback), `apple-touch-icon.png` (180px) and `icon-192.png` / `icon-512.png` for `manifest.json` (`icon-192.png` is also a `rel="icon"`, since Google Search doesn't use SVG favicons), all generated from the same design; keep them in step with the logo.
- **Headings:** h1 is the hero headline, led by the visually hidden name and title, h2 is a page section (`SectionLabel`, the small numbered label; the big lines under it, such as "Beyond the obvious bugs", are h3 or a paragraph), h3 is a card or group, h4 is a project tile. Sections use `aria-labelledby` pointing to their heading `id`.
- External links: `target="_blank" rel="noreferrer"`. Decorative images: `alt=""`.
- **Privacy:** never put a phone number on the site.
- **Render without a browser:** the build renders the page in Node, so no module may touch `window`, `document` or `localStorage` on import or while rendering. Read them in effects, event handlers or `src/index.tsx`, and pass what the browser knows in through `createAppStore(preloadedState)`. `src/entry-server.test.tsx` runs in Node and fails otherwise. The browser hydrates the copy, so its first render must match the build's: the same tree and no output that depends on time or the browser (the footer year carries `suppressHydrationWarning`). The e2e `prerender` spec fails if React has to redraw the copy.
- **Unit tests** live next to the code as `*.test.ts(x)`. Components that use styled-components must be rendered inside `<ThemeProvider theme={themeLight}>`. Mock data modules with `vi.mock` when a test needs specific content.
- **E2E tests** import `test`/`expect` from `e2e/fixtures.ts`, so GitHub is always mocked. Use role-based locators, and add new page behaviour to the e2e suite.
- Formatting: 2 spaces, double quotes, semicolons (Prettier defaults). Run `npm run lint`, `npm run typecheck` and `npm run format` before committing.
- Commits: short, lowercase, imperative English messages, matching the history (e.g. `fix tile background in dark theme`).

## Fixing bugs from GitHub issues

Bugs are reported as issues in `SzymonRojek/homepage` with the `bug` label (asked for by the user on 2026-10-17). Read the issue with `gh issue view <n>`, follow its "Done when" list, and treat its "Notes for whoever fixes it" as leads to check, not facts. Fix on `dev`; the Git workflow above still applies (ask before every push). Commit messages link the issue with `Refs #<n>`, never `Fixes`/`Closes`, which would close it at the merge. After the merge to `main` the issue stays open with the `to verify` label (add it when the user says the PR is merged), so it reads as waiting for a check, not for a fix. It is commented on and closed only once the user has tested the live site on their own devices: one comment with the cause, the fix (commit or PR link), what the tests proved and the user's check; post it only when the user says so. If the check fails, the user's findings go into a comment on the same issue (not a new one), the label comes off and the fix starts again from there.

Which tests to run depends on the change; as always, propose them and wait for a yes before running any:

- **Usually, locally, only what the fix touches:** the unit tests of the changed files (`npx vitest run <name>`), the e2e specs that cover the changed behaviour in both projects, desktop and mobile (`npx playwright test <spec>`), and `npm run lint` and `npm run typecheck`. CI runs the full suite (audit, coverage gate, build, all e2e, Lighthouse) on the push to `dev`, so it isn't repeated locally; Lighthouse is never run locally.
- **The full suite locally** only when the fix touches something the whole page shares (the theme, `GlobalStyle`, the layout, the prerender, the dependencies), or to find why CI failed.
- **A regression test for every bug,** unit or e2e, that fails on the old code and passes with the fix, so it proves it catches the bug.
- **The user's own phone** for anything a real device can change (scrolling, the address bar, touch, fonts): Playwright emulates a phone in desktop Chromium, and Chrome on an iPhone is WebKit, which the e2e suite doesn't run. Ask the user to check there before closing the issue.
