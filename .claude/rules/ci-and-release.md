# CI and release

Five workflows. Only a push to `main` deploys, and only through the job below; the Git workflow in CLAUDE.md is what keeps changes on that path.

- Every push to `main` or `dev`, and every PR into `dev` (Dependabot's, whose branches never see a push run), runs `npm audit` (shipped deps, high+), lint, `prettier --check` (a gate, so formatting is not something to remember), typecheck, unit tests with a coverage gate, build, e2e and Lighthouse budgets (`lighthouserc.json`, median of 3 runs, which also assert axe's Label in Name audit).
- `.github/workflows/safari.yml` runs the e2e suite in WebKit, Safari's engine, on `macos-latest` (`SAFARI=1`: Desktop Safari, iPad Pro 11 upright and landscape, iPhone 17, iPhone SE; tablets run only the untagged tests): by itself at 07:00 UTC on the 1st of every other month, and from "Run workflow" whenever a change might need it (the user's choice: a one-page site doesn't need Safari on every push; the scheduled run is the reminder, and GitHub emails when it fails). Not part of the deploy gate. GitHub turns scheduled workflows off after 60 days without a commit in a public repo, and emails before it does; re-enable it from the Actions tab.
- `.github/workflows/mutation.yml`: Stryker with 4 workers, writing the score per file to the run summary and uploading `reports/mutation` as the `mutation-report` artifact. It runs on the 15th of each month and from "Run workflow", with two optional inputs: `mutate` (a glob, for one file) and `since` (a ref, which mutates only what changed, through `scripts/changed-mutants.ts` so the config's exclusions still hold). A scheduled run mutates everything, since on the default branch there is nothing to compare against. Stryker 10 has no `--since` of its own, and `incremental` only helps a repeated run on the same machine, never a fresh runner. Not part of the deploy gate.
- `.github/dependabot.yml` opens monthly npm and GitHub Actions updates against `dev`, holding a new version for seven days first, and groups react with react-dom so the pair can never arrive as two failing PRs. Dependabot's alerts are on; its automatic security PRs are off, since every advisory it has raised has been in a dev-only transitive and the audit gate already stops a shipped one. Most need a breaking update (`npm audit fix --force`) and are left alone. Where a plain `npm audit fix` settles one in the lockfile alone, apply it by hand instead, as on 2026-10-24 (`body-parser`, `fast-uri`), and check that `npm audit --omit=dev --audit-level=high` stays clean afterwards. Major updates of `eslint`, `@eslint/js` and `typescript` are ignored: `eslint-plugin-react` supports ESLint 9 only and `typescript-eslint` supports TypeScript below 6.1. A PR from `dev` into `main` carries the check from the push that created the commit, since GitHub attaches a check to the commit rather than to the event; that is why there is no `pull_request` trigger for `main` and why one commit no longer runs twice. Merge a Dependabot PR only when its CI is green, and run `npm ci` locally after pulling dependency changes. When the bump includes `@playwright/cli`, run `npm run skills:refresh` too: the three Playwright agent skills are copies in `~/.claude/skills`, so a bump leaves them describing the previous version.
- Only pushes to `main` (merged PRs) deploy: the `deploy` job publishes the `dist/` its run built and tested with GitHub's own Pages actions (`upload-pages-artifact`, `deploy-pages`), through the `github-pages` environment. Pages' source is GitHub Actions, not a branch, so nothing else can publish the site, and there is no manual deploy command.
- Every workflow's token only reads (`permissions: contents: read`); the deploy job alone gets `pages: write` and `id-token: write`. Checkouts keep no credentials (`persist-credentials: false`), so the steps that run other people's code (`npm ci`, the build, the tests) can't push. Every action used is GitHub's own (`actions/*`).
